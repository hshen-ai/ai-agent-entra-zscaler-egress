Entra ID web-app sign-in, extended with Zscaler proxy authentication

What is actually reused

"Reuse" here is four specific things, not a general resemblance. Each one is why the proxy leg needs no second login and no second credential store:

  1. The sign-in itself. Steps 1–9 happen once, in the browser. The user never sees a prompt for the proxy. Steps 10–17 are entirely server-to-server.
  2. The user's access token, as the assertion. The On-Behalf-Of exchange at step 10 presents the same token the web app received at step 7 as its assertion. Entra therefore knows the request is made on behalf of a user who has already authenticated interactively — including any MFA and the consent from step 5.
  3. The signing keys. The Token Validator at step 16 fetches jwks_uri from the same tenant that signed step 6. It is not a separate trust anchor bolted on for the proxy; the proxy trusts exactly the tokens the sign-in produced. This is the load-bearing reuse — it is what makes the identity on the wire the same identity that logged in.
  4. The identity, end to end. The oid from the id token is the userId on the database row the agent writes through MCP; the email claim from the same token is the username Zscaler logs against the Bedrock request. One login, one human, visible in both planes.

The two things this does not do

The MCP hop at step 12 is not proxy-authenticated, and cannot be. It is a loopback call inside one container. Proxy authentication only applies to explicit-proxy egress, so there is no JWT on that hop; the token it carries is the todo0-audienced OAuth token, which is a different control. A diagram that drew a Zscaler connector on step 12 would be wrong.

The proxy must be explicit, not a default route. Traffic that reaches the internet over a plain default-route tunnel bypasses JWT authentication silently and open — it succeeds, and nothing in the response says the identity was never checked. The tell that authentication is genuinely in force is step 14: omit the header and the proxy must answer 407 with a Bearer challenge. If omitting it still yields a connection, the egress path is not the one drawn here.

Session level and process level are two different identities

Step 11 mints a token per logged-in session. An agent also makes calls that belong to no session — start-up, health checks, background work — and those need a separate, process-level identity of their own. The two are deliberately not fallbacks for each other: a session with no token must fail with a 407 rather than quietly borrow the process identity, because attribution in the proxy log is the entire point of doing this.

In this reference implementation the Entra path ships the session level only — GET /api/zia/status reports {"session":{…},"process":null}. A process-level workload identity is an extension point: it needs a non-interactive credential of its own, and must stay separate from every user session.

What has to exist on the Zscaler side

A ZIdentity Token Validator for the Entra issuer. Issuer https://login.microsoftonline.com/<TENANT_ID>/v2.0, JWKS URL …/<TENANT_ID>/discovery/v2.0/keys, Subject Claim email, and a required claim aud = <ZIA_EGRESS_APP_ID> — the last is what stops a token issued for another application in the same tenant from authenticating to the proxy. Masked lab example: https://login.microsoftonline.com/cddbxxxx-xxxx-xxxx-xxxx-xxxxxxxxf7c6/v2.0, aud = a015xxxx-xxxx-xxxx-xxxx-xxxxxxxxc4d6.

A ZIA user per identity, whose username equals the token's email claim — which Entra fills from the user's mail attribute. A token whose email matches no ZIA user is validly signed and still refused with 407.

The explicit proxy, with JWT authentication enabled for that traffic — <ZIA_PROXY>, e.g. 185.46.xxx.xxx:80 or gateway.<zscaler-cloud>.net:80. ZIdentity's "Test Token" checks only signature and expiry; the acceptance test is step 14's 407 next to step 17's 200.

Extension verified end to end: headless sign-in through Entra's own login pages → strategy: obo, connected: true → a todo written under the user's oid (userId=9b5bxxxx-…) → read back by todo0 under its own independent login.
